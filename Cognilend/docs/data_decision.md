## 1. Loan.csv target investigation: blocked

`Loan.csv` is not in the repository. Step 0 searched the project folder and the home directory to depth 4 and did not find it. The investigation tooling is ready and tested:

- `loaders.target_investigation(df, target='Status')` gives, for every column, the share of missing or `-1` values within each class, ranked by the gap between classes.
- `loaders.pricing_explains_target(df)` measures the precision and recall of "all pricing fields absent" as a predictor of `Status == 1`.

**Working hypothesis (unverified):** the description we were given matches the public Kaggle "Loan Default" dataset. That description says `Status = 1` is 24.6% of rows, and that `rate_of_interest`, `Interest_rate_spread` and `Upfront_charges` are absent exactly when `Status = 1`. If so, `Status = 1` means *default or not priced*, not *approved*. Pricing fields are filled in once a loan is priced, so they leak the target and must be dropped before any benchmark. **This will be confirmed or rejected with printed evidence once the file is supplied.** Until then no claim about Loan.csv appears in the report.

## 2. Why the primary dataset was regenerated rather than reusing the team file

1. **No generator or seed exists** for `loan_applications_raw.csv`, so it cannot be reproduced. The brief requires a seeded, deterministic generator that produces the same file hash on every run.
2. **Its label mostly re-encodes the policy rules.** In that file a rule violation led to rejection in about 96% of cases (`docs/dataset_report.md` §1.1, §7). A model trained on it largely re-learns R1–R7, which the rule layer already enforces.
3. The new generator keeps the team file's documented schema, value formats, spelling variants and defect counts, so the cleaning knowledge in the prototype still applies.

## 3. How the label is generated

The label is **not** a function of the policy rules. It comes from a latent repayment-risk score:

```
score = 0.8·z(income_stability) − 1.4·z(log1p FOIR) + 1.3·z(CIBIL) + 0.5·z(log1p experience)
        + 0.5·z(min(collateral/loan, 3)) − 0.6·[new to credit] + group_bias(gender)
label = Approved  if  score + Logistic(0, 0.5) ≥ the 41.5th percentile   (→ 58.5 % approved)
```

- `income_stability` is latent and not written to the file. It is higher for Salaried than SEP, and higher for SEP than SENP. It rises with experience and carries random noise. CIBIL is mildly correlated with it.
- FOIR uses the indicative rates in `policies_v1.yaml` to compute the proposed EMI.
- Age, age at maturity, the RBI LTV slabs, the minimum-income rule and the minimum-experience rule play **no** part in the label. The rules act as an independent gate in L1.
- `group_bias` is **−0.25 for Female and −0.40 for Transgender** (0 for Male). It is a small historical bias injected on purpose, so the L4 fairness audit has a known signal to detect. Income also carries a 15% gender gap. Gender is never a model input.
- All weights are in `config/synthetic.yaml` (`latent`).

### Evidence that the label and the rules are independent

Measured by `scripts/describe_synthetic.py` and saved to `artifacts/reports/synthetic_profile.json`. The rule checks are a diagnostic reimplementation of R1–R7; the real engine is built in Step 3.

| Measure | Value |
|---|---|
| Rows violating at least one rule (R1–R7) | 34.3% (team file: 32.9%) |
| Approval rate among rule violators | **27.2%** (team file: ~4%) |
| Approval rate among compliant rows | 74.9% |
| Accuracy of "approve if no rule is violated" | **0.742** |
| Accuracy of the noise-free latent score (the achievable ceiling) | 0.902 |
| 5-fold CV accuracy, entropy tree depth 4, crude features (sanity check only) | 0.803 |
| 5-fold CV accuracy, Random Forest, same features (sanity check only) | 0.863 |

The two models above use crude features only to show that the data is learnable. They are not the Step 4 model. Rule violators are still approved less often than compliant applicants. That is expected, because CIBIL and FOIR drive both the rules and repayment risk. Even so, the rules alone explain only 74% of labels.

Per-rule violation rates: R1 2.5%, R2 3.5%, R3 10.5%, R4 17.5%, R5 2.3%, R6 0.9%, R7 5.9%.

Label approval rate by gender on unique rows: Male 0.593 (n=7,005), Female 0.568 (n=2,793, DI 0.957), Transgender 0.508 (n=67, DI 0.856, small sample).

### Calibration note

The first parameter set produced 43.6% rule violators and a noise-free ceiling of 0.847. Two applicant-behaviour parameters were then changed: loan-size multiples were reduced, and 85% of applicants now pick a tenure that ends by age 60. Noise was reduced from 0.75 to 0.50, so the ceiling (0.902) is close to the 85–89% achievable accuracy documented for the team dataset. The label formula was not changed. **Noise was not tuned against the Step 4 tree or its 80% KPI.**

## 5. Data contract

`config/data_contract.yaml` defines the schema and `src/cognilend/data/contract.py` loads it. For each field the schema gives the name, dtype, unit, valid range or allowed values, whether the field is required, whether it is protected, and whether it may be a model input. The contract describes one application in **canonical** form: raw spellings such as `HL` or `Rs. 27,90,000` are mapped in Step 2, before validation.

- **Protected** (stored and audited, never model inputs): `Gender`, `Marital_Status` and the derived `Age_Band`.
- `Age` is used by rules R1 and R2 and to derive `Age_Band`. It is **not** a direct model input. Whether `age_at_maturity` may be a model feature is decided in Step 2, because it carries age information.
- `Property_Area` is excluded from the model because it may act as a geographic proxy for protected groups.
- Ranges check plausibility, not credit policy. Age 19 is valid input that R1 then rejects; Age 999 is refused before any rule runs.
- `validate()` never raises. It returns a list of messages, and an empty list means the record is valid.
